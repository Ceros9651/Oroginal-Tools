## Context

新規プロジェクト（Original-Timer）で、区間タイマーをゼロから実装する。既存コード・既存 spec はなく、依存関係やスタックの制約も未確定。要求は proposal.md と 2 つの spec（`interval-schedule` / `countdown-timer`）で定義済み。

主な性質:
- 単一ユーザーがローカルで使うツール。サーバー側処理・認証・複数ユーザー同期は不要。
- コア難所は「正確な残り時間のカウントダウン」と「区間の自動遷移」という状態遷移ロジック。
- UI は「区間リストの編集」と「実行画面（残り時間・現在種別・操作）」の 2 面。

## Goals / Non-Goals

**Goals:**
- 追加依存・ビルド不要で動く、自己完結した単一ページのタイマーを実装する。
- 区間リストの追加／並べ替え／削除と、開始・一時停止・再開・リセットを提供する。
- 分単位で登録し、残り時間は「分：秒」で表示する。区間 0 で自動遷移＋通知する。
- タイマー計時が経過実時間ベースで正確であること（後述の drift 対策）。

**Non-Goals:**
- 複数スケジュールの保存・切り替え、クラウド同期、アカウント管理。
- サーバーバックエンド、モバイルネイティブアプリ。
- 秒単位・時間単位での区間指定（単位は分に固定）。

## Decisions

### 決定1: スタックは依存ゼロのバニラ Web（HTML + CSS + JavaScript）
単一ファイル群（`index.html` / `style.css` / `app.js`）で完結させ、ブラウザで開くだけで動作させる。
- **理由**: タイマーはロジックが小さく、フレームワークのビルド基盤はオーバースペック。依存ゼロなら Windows 環境でセットアップ不要、レビューも容易。
- **代替案**: React/Vite（コンポーネント分割は綺麗だがビルド・依存が増える）→ 規模に見合わず却下。Electron（デスクトップ化できるが配布が重い）→ Non-Goal のため却下。将来フレームワーク化する場合もロジックを純粋関数に寄せておけば移行しやすい。

### 決定2: 計時は「終了時刻ベース」で行い、`setInterval` は表示更新のみに使う
残り時間を「毎 tick で 1 秒引く」のではなく、開始時に `endTime = now + 残りミリ秒` を保持し、表示更新時に `remaining = endTime - now` を再計算する。表示更新は `setInterval`（約 250ms）で行う。
- **理由**: `setInterval` はタブ非アクティブ時などに間引かれ、単純減算では時間がずれる（drift）。実時間から算出すれば累積誤差が出ない。
- **代替案**: 単純な 1 秒 `setInterval` 減算 → 実装は簡単だが精度要求（Goals）を満たせないため却下。

### 決定3: タイマー状態を有限状態機械（FSM）として明示する
状態を `idle` / `running` / `paused` / `completed` の 4 つとし、遷移（start / pause / resume / reset / tick-zero）を 1 箇所で管理する。現在区間は「区間リスト内のインデックス」で表す。
- **理由**: 一時停止・再開・自動遷移・完了が絡む挙動はバグの温床。状態と遷移を明示すると spec のシナリオと 1:1 で対応づけてテストしやすい。
- **一時停止の扱い**: pause 時は `endTime` から残りミリ秒を確定して保存し、resume 時に `endTime` を再計算する。

### 決定4: データモデル
- `Interval = { id: string, type: '作業' | '休憩', minutes: number }`（`minutes` は 1 以上の整数）。
- `Schedule = Interval[]`（順番そのものが実行順）。
- 実行状態 = `{ status, currentIndex, endTime | remainingMs }`。

### 決定5: 永続化は localStorage（任意・軽量）
編集した区間リストを `localStorage` に保存し、リロード後も復元する。実行中の状態は永続化しない。
- **理由**: サーバー不要でユーザー体験が向上する。Non-Goal の「複数スケジュール管理」には踏み込まず、単一リストのみ保持する。

### 決定6: 通知は画面表示＋任意の音
区間切り替わり・全完了は、画面上の明示的な表示（現在種別の切り替え・完了メッセージ）で通知する。加えて短い効果音（Web Audio）を鳴らす。ブラウザ通知 API は許可が必要なため任意扱いとする。
- **理由**: spec の「通知」を確実に満たすのは画面表示。音は補助。

## Risks / Trade-offs

- [タブ非アクティブ時にタイマー音や描画が遅延する] → 計時は終了時刻ベースなので残り時間の正確性は保たれる。再アクティブ化時に正しい残り時間へ即再描画する。
- [依存ゼロ構成ゆえテスト基盤も手薄になりがち] → コア計時・FSM・区間遷移を副作用のない純粋関数に切り出し、軽量なテスト（あるいは手動シナリオ）で spec のシナリオを検証可能にする。
- [localStorage が使えない／無効な環境] → 保存失敗時は握りつぶし、メモリ上のリストで動作継続する（機能低下のみ）。
- [多数の区間を登録した場合の UI 煩雑化] → 本リリースはシンプルなリスト UI に留め、グルーピングやテンプレートは将来課題とする。

## Open Questions

- 効果音は同梱アセットにするか Web Audio の合成音にするか（配布容易さから合成音を第一候補とする）。
- 並べ替え UI はドラッグ&ドロップか上下ボタンか（実装容易さから上下ボタンを初期案とする）。
